# PTran v1 design

Status: accepted design for the first implementation.

PTran is a Lean library for expressing optimization problems and certifying that
problem transformations preserve their **global** optimization meaning. It is
inspired by the proof-oriented interface of
[CvxLean](https://github.com/verified-optimization/CvxLean), but its semantic
core is deliberately independent of convexity and it has no numerical solver
backend.

The trust boundary is Lean's kernel: a transformation is accepted only when its
generated certificate type-checks.

## Scope

Version 1 provides:

- minimization and maximization problems;
- named constraints and unconstrained problems;
- global-equivalence certificates;
- substitution with a proof that the substitution covers every feasible source
  point;
- epigraph and hypograph transformations; and
- a mathematical problem printer.

PTran verifies a certificate supplied by a user or generated by a registered
transformation. It does not decide whether arbitrary optimization problems are
equivalent. Failure to build a certificate means only "not certified," never
"proved non-equivalent."

The initial project uses Lean 4.33 and a compatible pinned mathlib release.

## Problem declarations

The canonical input syntax starts with `problem`; `where` is neither needed nor
accepted between the binders and the objective.

```lean
noncomputable section

def original :=
  problem (x : ℝ)
    minimize (Real.log x)^2
    subject to
      positive : 0 < x
```

The surrounding `noncomputable section` is required by Lean for objectives
such as `Real.log`; purely computable objectives do not need it.

Maximization uses the same form:

```lean
def largestSquare :=
  problem (x : ℝ)
    maximize x^2
    subject to
      lower : -1 ≤ x
      upper : x ≤ 1
```

All v1 variable binders are explicitly typed and nondependent. Consecutive
binders may share a type:

```lean
def distanceSquared :=
  problem (x y : ℝ)
    minimize x^2 + y^2
```

The `subject to` block is optional. Within a constraint block, every constraint
has a distinct label. Labels are used for presentation and diagnostics and have
no effect on the mathematical meaning of the problem.

### Mathematical display

`#printp` displays a problem as mathematics rather than as its elaborated Lean
term:

```lean
#printp original
```

```text
minimize (Real.log x) ^ 2
over (x : ℝ)
subject to
  positive : 0 < x
```

For an unconstrained problem, the `subject to` section is omitted. The printer
uses `maximize` for objectives entered as maximization problems and groups
adjacent variables of the same type when possible.

`#printp` is a display command, not a second problem-definition syntax, and its
output is not required to be pasted back into a Lean term. Lean's built-in
`#print` command is not shadowed or modified.

## Semantic model

At its proof-relevant core, a problem consists of:

```lean
structure Problem (X : Type u) (V : Type v) where
  objective : X → V
  feasible : X → Prop
```

Here `X` is the complete decision-variable space and `V` is the objective-value
space. The surface syntax may attach binder names, constraint labels, and other
presentation information, but this metadata is semantically inert.

The core does not require an order on `V`. Ordering assumptions are introduced
only by certificate definitions and theorems that need them. This keeps a
problem reusable under different order structures and avoids baking convex or
numeric assumptions into the representation.

### One-way global improvement

For minimization problems `p : Problem X V` and `q : Problem Y V`, with an
appropriate preorder on `V`, a certificate

```lean
GlobalImprovement p q
```

contains a map from feasible points of `p` to feasible points of `q`. If `x` is
feasible for `p`, its image is feasible for `q` and satisfies

```text
q.objective (map x) ≤ p.objective x.
```

Thus `q` is globally no worse than `p`. The map is not required to be injective,
surjective, continuous, differentiable, or invertible.

### Global equivalence

```lean
GlobalEquivalence p q
```

contains a `GlobalImprovement p q` and a `GlobalImprovement q p`.
Global equivalence is reflexive, symmetric, and transitive; composition composes
the feasible-point maps and their objective inequalities.

This deliberately does **not** require a bijection of feasible sets. The two
directions are enough to preserve the global optimization facts that PTran
claims:

- feasibility and infeasibility;
- attained global optima, including a way to transport an optimizer in either
  direction;
- the globally optimal objective value when it is attained;
- exactly the same objective lower bounds (and therefore the same infimum
  whenever that infimum is defined); and
- unbounded-below behavior (and, for maximization, unbounded-above behavior)
  when the relevant strict-order hypotheses are available.

Optimizer cardinality, the identity of all optimizer points, and the topology
or geometry of the feasible set need not be preserved.

### Maximization

Maximization is normalized in the semantic core to minimization over
`OrderDual V`. Consequently the certificate engine needs only one orientation
of objective comparison. Presentation metadata records the user's objective
sense so that diagnostics and `#printp` continue to say `maximize` and use the
natural, non-dual order in displayed constraints.

## Reformulations

A reformulation declaration names both the transformed problem and its global
equivalence certificate:

```lean
reformulation certified / transformed : original := by
  substitute x := Real.exp u
  epigraph t
```

This declaration creates:

```lean
transformed : Problem _ _
certified : GlobalEquivalence original transformed
```

Each command in the body constructs a new problem and a certificate relating it
to the preceding problem. The reformulation runner composes those certificates,
so the final certificate directly relates `original` and `transformed`. The
generated declarations are accepted only if every proof obligation is closed;
the command never emits an admitted theorem.

Transformation variable names must be fresh, and generated constraint labels
must not collide with existing labels. Such collisions are reported at the
transformation step that introduced them.

### Substitution

```lean
substitute x := φ u
```

replaces the source variable `x` by the expression `φ u`, introduces the fresh
variable `u`, and pulls the objective and constraints back along that map. Other
decision variables remain in scope and may occur in `φ`.

In v1, the introduced variable inherits the type of the replaced variable.
This keeps the compact syntax unambiguous; type-changing substitutions can be
expressed through the semantic `Problem.pullback` API, and richer surface syntax
is reserved for a later version. The surface rewriter also does not yet support
an objective or constraint that shadows the selected decision-variable name in
a nested Lean binder; those cases can use the semantic API directly.

Pullback always supplies one direction of the equivalence: a transformed point
maps to the source point obtained by evaluating `φ`. The other direction needs
a **feasible coverage** proof. After fixing the retained variables, every
feasible source point must have some `u` for which `φ u = x`. Coverage is
required only on the feasible set; a global inverse, uniqueness, and injectivity
are unnecessary.

PTran first tries registered substitution rules. The v1 rule recognizes the
following first step for a single-variable source with an explicit `0 < x`
constraint:

```lean
substitute x := Real.exp u
```

It chooses `u = Real.log x` and discharges coverage with the exp/log identities.
For an unregistered map, the user supplies the coverage certificate explicitly:

```lean
substitute x := φ u using hCoverage
```

The command checks `hCoverage` against the coverage obligation inferred from the
current problem rather than trusting a transformation-specific axiom.

After substitution, proof-producing simplification is applied to the objective
and constraints. The final generated `Problem` uses the simplified expressions,
and a pointwise equivalence certificate connects it to the raw pullback. A
constraint is removed only when Lean proves it is `True`. In the exp/log example,
this simplifies
`Real.log (Real.exp u)` to `u` and proves `0 < Real.exp u`, so the original
positivity constraint disappears.

### Epigraph

For a minimization problem with objective `f x`, the command

```lean
epigraph t
```

introduces a fresh objective variable `t` and constructs

```text
minimize t
over (x t)
subject to
  <existing constraints>
  epigraph_t : f x ≤ t
```

The source-to-target certificate chooses `t = f x`; the target-to-source
certificate drops `t` and uses the epigraph inequality. Neither direction uses
convexity.

For a maximization problem, the dual command is:

```lean
hypograph t
```

It adds `hypograph_t : t ≤ f x` and maximizes `t`. Applying `epigraph` to a
maximization problem, or `hypograph` to a minimization problem, is rejected with
a sense-specific diagnostic.

### Complete introductory example

For

```lean
def original :=
  problem (x : ℝ)
    minimize (Real.log x)^2
    subject to
      positive : 0 < x

reformulation certified / transformed : original := by
  substitute x := Real.exp u
  epigraph t
```

the mathematical view of `transformed` is:

```text
minimize t
over (u t : ℝ)
subject to
  epigraph_t : u ^ 2 ≤ t
```

The forward map from the original problem can choose
`(u, t) = (Real.log x, (Real.log x)^2)`. The reverse map sends `(u, t)` to
`Real.exp u`. The epigraph inequality supplies the required objective comparison
in the reverse direction.

## Nonconvex problems

Convexity is not part of `Problem`, `GlobalImprovement`, or
`GlobalEquivalence`. The same definitions and transformation commands apply to
convex, nonconvex, discrete, and mixed-domain problems whenever Lean can verify
their proof obligations.

This is possible because certificates compare all feasible points globally.
PTran does not infer global equivalence from first-order conditions, Hessians,
KKT conditions, or local arguments. A nonconvex substitution or epigraph is
valid for exactly the same reason as a convex one: explicit feasible-point maps
and kernel-checked objective inequalities establish both directions.

As a consequence, global minimizers and values are within scope, while local
minima, stationary points, basins of attraction, solver trajectories, and KKT
points are not promised to correspond.

## Extensible certificate relations

The reformulation runner is parameterized internally by a composable certificate
relation: the relation supplies identity and composition operations, and each
transformation step supplies a certificate in that relation. It is not keyed by
a closed `CertificateKind` enumeration.

In v1, the public `reformulation` command instantiates this machinery with
`GlobalEquivalence`. A future

```lean
relaxation lowerBound / relaxed : original := by
  ...
```

can instantiate the same runner with the one-way `GlobalImprovement` relation.
Moving from an equivalence certificate to a one-way certificate will use an
explicitly named projection or lift; there is no implicit `Coe` that can silently
discard half of an equivalence proof.

The exact relaxation syntax and its claimed bounds are reserved for a later
design. V1 must preserve this extension seam but does not expose an unfinished
relaxation API.

## Diagnostics and failure behavior

Elaboration should fail locally and explain the unsatisfied obligation when:

- a problem binder lacks a type or depends on an earlier decision variable;
- constraint labels, transformation variables, or generated labels collide;
- substitution coverage cannot be inferred and no valid `using` proof is given;
- a transformation is incompatible with the objective sense; or
- `#printp` is applied to a declaration without PTran problem presentation data.

The diagnostic wording must distinguish inability to certify a step from a
mathematical proof that the step is invalid.

## Non-goals for v1

Version 1 does not provide:

- a numerical solver or an interface to one;
- disciplined convex programming analysis or automatic convexity proofs;
- automatic discovery or decision of arbitrary problem equivalence;
- automatic proofs of non-equivalence;
- preservation of local optima, stationary points, KKT points, multiplicity of
  optimizers, or algorithmic convergence behavior;
- a requirement that equivalent problems have bijective feasible sets;
- a public relaxation command; or
- dependent decision-variable binders.

These exclusions keep the initial library centered on a small, auditable global
semantics and proof-producing transformations.
